# Learnings

- Two concurrent orders can both pass the capacity check before either commits (Stage 0). Not fixed — comes back in Stage 6 with Redis-based seat holds.
- Stage 2: `events-service` is now a standalone service with its own database (`events-db`, port 5433) and no knowledge of orders at all. `orders-service`'s local `Event` entity/table is gone; capacity checks go through `EventClient` (a `RestClient` call to `events-service`).
- Splitting the database forced dropping the `orders.event_id -> events.id` foreign key and its index — that FK was added back in Stage 0 specifically anticipating this, since a FK can't reach across two separate databases.


- "GET /events/{id}" now means two different things depending on which service you ask: events-service returns the canonical event, orders-service exposes a separate `GET /events/{id}/availability` that combines the remote event with its own order data (ticketsRemaining). Kept the aggregation in orders-service since that's the side that owns the order data needed to compute it — but it's worth noticing this is exactly the kind of read-aggregation a dedicated gateway/BFF would normally own once there's a third consumer of it.
- Env var -> property binding gotcha: Spring's relaxed binding *strips* dashes from property names when converting to env var form, it doesn't map them to extra underscores. `events-service.url` would need `EVENTSSERVICE_URL`, not `EVENTS_SERVICE_URL`. Avoided it by using `events.service.url` (dot-only path) so it follows the same convention as `spring.datasource.url` -> `SPRING_DATASOURCE_URL`.
- Once `orders-service` calls out to `events-service` for capacity, the check-then-act race gets worse, not better: two network hops instead of one in-process check widen the window instead of closing it. Deliberately not fixing this in Stage 2 — it's the same class of problem Stage 6's Redis holds exist to solve, and reaching for a distributed-transaction fix now would be solving it before feeling why it's needed.
- Watched Stage 2 fail with events-service stopped (its required "done when"): `EventClient` originally only caught `HttpClientErrorException.NotFound`, so a stopped events-service produced a `ResourceAccessException` that went uncaught all the way to a generic, opaque 500 — indistinguishable from any other bug. Fixed by catching `ResourceAccessException` and mapping it to a clean 503, so callers can now tell "event genuinely doesn't exist" (404) apart from "the service that would know is unreachable" (503).
- Still open: `RestClient` has no timeout configured. A cleanly *stopped* events-service fails fast (connection refused); a *hung* one (up, but not responding) would hang orders-service's thread instead, which is a worse failure mode than the one we just fixed. Not addressed yet.

## Stage 2 reflection: should this split exist?

**Context.** Stage 0 left us with a single, working service. Splitting it into two forces real questions that reading about it doesn't answer: what happens when one service becomes two, where should the boundary actually sit, and how do you implement and test a system where two services have to communicate over a network instead of a single in-process call.

**Decision.** Everything related to events went into `events-service`, everything related to orders stayed in `orders-service`. They communicate over HTTP: `orders-service` calls `events-service` to check available capacity and fulfill orders.

**Consequences.** We tested and watched the system's behavior in different scenarios — most importantly what happens when one service is down and the other depends on it. With `events-service` stopped, orders could no longer go through, since placing or cancelling an order depends directly on `events-service` being reachable. The failure had to be mapped explicitly, from a generic 500 to a handled 503 naming the dependency that's down. The foreign key between `orders.event_id` and `events.id` was lost, since the two tables can no longer reference each other directly across separate databases. The cost of setting up and maintaining two services — two Dockerfiles, two databases, two healthchecks, more Compose wiring — is real, and bigger than running one.

**Benefits.** Learning how to weigh the cost of a network boundary: what coupling actually costs, what cohesion means for the modules involved, and how ignoring either comes back to bite you later.

**Alternative considered.** A modular monolith — one deployable, with events and orders as separate, enforced internal modules instead of separate services — would have given the same boundary discipline (an explicit contract between the two areas, no reaching into each other's data) without paying for a network hop in the hot path, a second database, or a new class of failure that didn't exist before.

**When this calculus flips.** The heuristic isn't "never split" — it's "split when something is genuinely reused elsewhere, or needs to scale, deploy, or fail independently of everything around it." A masterdata service (venues, ticket types, pricing) would be a stronger case for its own service, since it would realistically be read by multiple independent consumers — orders, a future POS system, staff scheduling, reporting — each with a different access pattern and change cadence, rather than by one thing that shares its consistency boundary.

**Verdict.** For a system shaped like this one, the split isn't architecturally justified — events and orders share a consistency boundary (the capacity check), and the coupling wasn't removed by splitting them, it was relocated from a foreign key to a synchronous HTTP call with a hardcoded URL and a new failure mode. It was still worth building for what Stage 2 set out to teach: what a network boundary actually costs, first-hand, instead of in the abstract.

## Stage 3

- `orders-service`'s URL namespace originally overlapped with `events-service`'s (`GET /events/{id}/availability`, `POST /events/{id}/orders` both nested under `/events`), which made clean Traefik `PathPrefix` routing impossible without priority rules or regex. Fixed at the API level instead of the router level: flattened everything orders-service owns under `/orders` (`POST /orders` with `eventId` in the body, `GET /orders/availability/{eventId}`). Each service now owns one clean, non-overlapping prefix — routing by service ownership, not by resource nesting.
- Real finding, not yet addressed: with Traefik in front and the host ports removed from `orders-service`/`events-service`, clients only know one hostname — but internally, anything else on `shared-network` can still reach either service directly (e.g. `http://orders-service:8080/orders/1`), completely bypassing Traefik. "Neither service publishes a port to your host" only closes the external path, not the internal one.
- Considered restricting Docker networking now so only Traefik can reach the services. Decided against it for now: it would close the container-to-container bypass, but it doesn't touch the actual risk (right now, *any* request through Traefik succeeds with zero authentication — no token, no login, anyone can read any order). Network segmentation can only distinguish "inside the network" from "outside," not "which customer is this" — so doing it before real auth exists would look like a security improvement while leaving the actual gap (unauthenticated access to everyone's data) completely open. Deferred until after Stage 4's identity-based auth exists, then added as a second, complementary layer (defense in depth) — not a substitute for it.
